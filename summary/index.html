HTML-first React: Results Summary

Merge PR #24, turn on enableFlightHtmlFirst, and have the framework pass onElidedRow: true on the one Flight render that feeds HTML SSR. Compared with stock React main (same tip, flag off):

  • ~43% smaller gzip HTML downloads across 41 pages (sum), ~79% less inlined Flight (the JS payload in the document)
  • ~3.2× Waku host-page throughput (3.19×, range 3.15–3.24, TTFB 0.48×) with a one-line framework change
  • No change for users or authors: same components and APIs; the 41-page correctness corpus passes in Chromium

What changes

One experimental flag, off by default. With it on, a request elides only when the framework opts in with onElidedRow: true. Static Server Component host markup in host position (host children, Suspense children, Client Component children, and the entries of a root element map such as {page, layout}) is then left out of the browser Flight payload and adopted from the SSR HTML. Non-children props (panels, fallback, …) stay in the payload.

Nothing changes for apps until the flag is on, and nothing is elided unless the framework opts in, so responses that go straight to the browser (navigation, refetch, action results) are never elided by accident.

Correctness (UX / DX)

  • Same public component model: authors do not mark trees or change JSX for the win.
  • Hydration adopts server DOM for elided regions; interactive client islands keep working.
  • 41-page corpus: 41/41 in Chromium at 8dd5e5f61d (hydrated and post-interaction DOM equal to stock, no console or hydration errors, SPA navigation to a full payload equal to the hydrated page). The DOM compare canonicalizes style spacing, zero-length CSS units and attribute order. Firefox and WebKit passed on earlier tips and were not re-run at this one.
  • Waku: hydrates, counters interactive, 0 console errors, SPA navigation renders all 1000 rows.
  • On navigation the full payload re-creates the elided regions (the old DOM is not trusted, because the new page can differ); client components keep their state.
  • Deferred mounts (modal, ClientOnly) and Suspense client-render recover via the framework-supplied onElidedContentMissing. Without it the stub suspends and reports an uncaught error rather than blanking quietly, so it is recommended.
  • Head DOM is not always byte-identical (preload hints can differ); unique resources still match.

How it works

Today an RSC initial response ships the same static server markup twice: Fizz HTML to paint, and an inlined Flight payload to hydrate. With enableFlightHtmlFirst, React withholds static Server Component host trees that sit in host position from the payload the browser receives and leaves a small $J stub. SSR and the browser need different things: SSR needs the withheld content to write the HTML, the browser only needs a stub because the HTML is already on the page.

The framework opts in by passing onElidedRow: true on the Flight render that feeds SSR. React then collects the withheld rows in an internal registry keyed by a :Q row in the stream. The first in-process createFrom* claims it for SSR; the browser isolate has an empty registry, sees the stubs, and adopts the HTML. A function onElidedRow / onElidedValue is the override for out-of-process consumers.

React cannot infer whether a stream is going to the browser: the stream is the same bytes either way. The framework already knows (Waku routes RSC/ URLs separately; Next.js sends an RSC: 1 header), which is why the opt-in is one option on the SSR-feeding render and every other response needs no change.
