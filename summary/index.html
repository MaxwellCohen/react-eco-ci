HTML-first React: Results Summary

Bottom line. React Server Components pages send their content twice on first load. For the part of a page produced by server code, we can stop doing that. Our test pages get up to 68% smaller over the wire (48% on the 1000-row page), with byte counts that reproduced exactly on a fresh rerun. It only takes effect when a framework opts in; Waku (patched locally) shows -55% / -46% / -33% client gzip on three page shapes.

A second idea, replacing Fizz's per-boundary scripts with a declarative HTML mechanism (DPU), did not hold up on rerun. We do not recommend it as a general replacement. Details in the honesty section.

Recommendation: pursue the Flight HTML-first work with a framework opt-in, using Waku as the reference integration. Park DPU unless a boundary-heavy use case appears.

1. The problem

  • An RSC page is delivered as HTML (Fizz) so the browser can paint, plus an inlined copy of the same content in Flight format so React can hydrate. Static markup (inline CSS, JSON-LD, plain elements) rides along twice and is dead weight the second time.
  • Flight is 37% to 76% of the document on our stock test pages (Waku: 48% to 54%).
  • Separately, Fizz streams each Suspense boundary with its own small inline $RC script. A page with hundreds of boundaries has hundreds of scripts.

2. The proposal

The HTML is the source of truth on first load. Flight is for navigation and actions. All flags are default off; nothing changes unless a framework opts in.

  1. Host elision: static host elements rendered by server components are not repeated in the initial Flight payload.
  2. Payload dedupe: long repeated strings and reference paths are sent once.
  3. HTML-first: static <style> and JSON-LD blocks stay out of Flight, and in-process SSR hands the live nodes over instead of re-serialising them. (An earlier iteration also had unstable_pruneForBrowser, an author assertion that a client component's props are unneeded in the browser. The latest commit on PR #21 removed it; client components now always keep full props. The measurements below were taken before that removal, so the "pruned" Waku row reflects the removed variant.)
  4. Fizz DPU (separate track): replace per-boundary scripts with <template for> declarative patching.

4. What did NOT reproduce (Fizz DPU)

We reran everything from scratch. Flight byte counts reproduced to within 0.01% to 0.04%. The Fizz DPU numbers did not. The original claims were too optimistic, and we are retracting them.

Reading: the byte win is modest (about 4% gzip) and appears only above roughly 550 boundaries. Brotli breaks even near 300. The main-thread cost is real and grows with boundary count. Not recommended as a general replacement. A zero-batching variant shows content earlier (LCP about 65 to 95 ms vs 330 to 380 ms) but costs 20+ layouts and up to 2.6x main-thread time.

How much to trust timing: the machine was not fully quiet, the same code drifted 20% to 50% between processes, so only within-process ratios are used. Node 26, Chrome 157 only. Byte counts are exact; timing is noisy.

5. Risks and limits

  • Client-component props are the floor. Only server-component output is elided; client components keep full props (the 1000-row client-row page only gets dedupe, -7% gzip).
  • Elision is static-only. Anything with a client component inside keeps its host skeleton.
  • Framework opt-in is mandatory. Flags alone change under 1% (Waku measured +0.06% to -0.6%).
  • Navigation still gets full Flight, and an elided region remounts on the first client navigation. Static prerendered pages are unaffected.
  • Dedupe reverses an upstream protocol decision and needs React maintainer sign-off.
  • Pruning was an author assertion (wrong means inert UI). It has been dropped from the current PR for that reason.
  • Chrome only. No Firefox or WebKit runs. Nothing is merged upstream.

6. Decisions and next steps

  1. Recommended: continue the Flight HTML-first stack (PRs #12 to #15, #21) and agree a framework opt-in contract, with Waku as the reference integration. Turn the local Waku patch into a proposal for Waku maintainers.
  2. Get maintainer feedback on payload dedupe, since it changes a protocol decision.
  3. Park DPU (PR #22). Revisit only for a use case with well over 500 Suspense boundaries per page, and fix the main-thread cost first.
  4. Before any rollout: re-run Waku with timing, and test Firefox and WebKit.

  • Flight: branch rsc/5-html-first-flight at 1930da7cf8, four production builds with flags off / elision / elision+dedupe / all. Flags are compile-time, so each is a separate build.
