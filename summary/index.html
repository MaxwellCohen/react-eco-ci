HTML-first React: stop sending static markup twice

On first load, a React Server Components page sends its static markup twice: once as HTML, so the browser can paint, and again inside the Flight payload, so React can hydrate. For content that never changes on the client, the second copy is wasted bytes, server time and hydration work.

The proposal: a React flag, enableFlightHTMLFirst, and one option a framework passes on the Flight render that feeds its HTML. Flight writes a small stub in place of static host markup in the bytes for the browser, the HTML renderer still gets the real elements, and the browser adopts the DOM the HTML already contains. Navigations, refreshes and actions are unchanged, and so is every app that doesn't opt in.

The result: gzipped downloads 42% smaller across 41 test pages, a 1000-row table served at 3.0× the requests per second on Next.js and 3.6–4.1× on Waku, Next.js's own end-to-end suites passing with it on, and no page more than 10% slower to hydrate. It builds on Andrew Clark's Flight tee (react/react#38313). It is an experiment in a fork, not part of React.

What a framework does

A framework already knows which Flight render feeds its HTML; only that one opts in. Through the tee, SSR reads the render directly instead of parsing bytes. The framework tells React when the HTML is done, so React can then send anything the HTML didn't render.

// Server: the Flight render that feeds HTML
import {renderToReadableStream} from 'react-server-dom-webpack/server';
import {createTee, createFromTee} from 'react-server-dom-webpack/client';
import {renderToReadableStream as renderToHTML} from 'react-dom/server';

const tee = createTee(serverConsumerManifest);
let htmlDone, htmlFailed;
const htmlFirst = new Promise((res, rej) => { htmlDone = res; htmlFailed = rej; });

const flight = renderToReadableStream(app, clientManifest, {htmlFirst, tee});
const html = await renderToHTML(<Root payload={createFromTee(tee)} />);  // as today
html.allReady.then(htmlDone, htmlFailed);              // then React sends what HTML didn't render
// Inline `flight` into the HTML, as today.

// Browser: hydrate as today, with a way to recover
createFromReadableStream(inlinedFlight, {onMissingHTML: () => refetchRoute()});

The working patches change 164 lines in Waku and 303 in Next.js (where it sits behind experimental.htmlFirstFlight), including recovery and caching. Without the option, or with the flag off, output is byte-identical to React today.

What gets left out

Markup is stubbed when it is plain host output of a Server Component in a position React renders in place: children of host elements, Fragments and Suspense boundaries; what's inside the children of Client Components such as layouts and slots; and plain data around elements, such as a framework's route tree.

It is never stubbed when the client could need it with no server DOM behind it, or when a stub would cost more than it saves:

  • Client Components, and any prop other than children.
  • The element a Client Component receives as children itself, so cloneElement, asChild slots and type checks still work.
  • Forms, inputs, images, SVG, head elements, template, and lone void elements such as <hr>.
  • Elements under about 48 bytes, where a stub saves almost nothing and adds a component in the browser.

What a stub does in the browser

  • During hydration it adopts the server DOM. The stub is one component with one hook.
  • Content the HTML never rendered, such as a closed modal's children or a hidden tab panel, arrives at the end of the stream once the framework says the HTML is done. The stub renders it when it mounts, with no extra request. If the HTML render failed, every stubbed row is sent.
  • When it mounts again, for example after Back navigation, it rebuilds from a snapshot of the HTML it adopted.
  • When a later full payload arrives, from a refresh or an action, React keeps the stub and its DOM if the new element renders the same DOM. Patching changed content in place is a separate follow-up, PR #31.
  • If content is still missing, because React renders a boundary on the client for a reason the server never saw, React calls onMissingHTML and the framework refetches.

Next.js details

The patch is on branch html-first/16.4-tee-signal, turned on with experimental.htmlFirstFlight: true.

  • Dynamic pages and PPR resumes opt in on the HTML render. RSC requests (navigation, refresh, actions) still get full payloads.
  • Prerendered pages keep their stored payload complete for navigations and prefetches; only the copy inlined in the HTML leaves static markup out. No Server Component runs twice.
  • Cache Components work, including cached navigations.
  • Recovery through onMissingHTML refetches only the current route and keeps Next.js's client caches.

Correctness

  • Next.js end-to-end tests: 52 of Next.js's own suites in production mode with Turbopack, covering the app router, navigation, the back/forward and client caches, parallel and intercepted routes, server actions, static generation and ISR, error pages, metadata, Cache Components and PPR. With the option on, 871 tests pass and none fail. With it off, rsc-basic, app-action and navigation pass 172.
  • 45 test pages in browsers: each page is loaded with the feature off and on in Chromium 139 and Firefox 159. The check compares the hydrated DOM, the DOM after interaction, and the DOM after a client navigation to a full payload, and fails on any console or hydration error. All 45 pass. WebKit 18.4 passed all 41 original pages on an earlier build; it was not run on this one.
  • Live demos: on the Next.js and Waku demos below, every page hydrates with no console errors, counters respond, and opening the modal or a hidden tab shows its content with no extra request.
  • React's own tests: the six HTML-first suites (136 tests) pass on three release channels, the Flight suites have no failures that don't also happen upstream, and Flow passes on 17 renderers.
  • Edge cases: 23 tests, each demanding exactly the behavior with the feature off. 19 pass; the other 4 are explained below.

Trade-offs and open questions

  • It depends on the Flight tee. react/react#38313 has to land first, with enableFlightTee on in the channel a framework uses. The demo builds force both flags on.
  • Four edge cases differ from the feature off, because they need data the feature leaves out on purpose. When React renders a boundary on the client for a reason the server never saw (a context change before the boundary hydrates, or children hidden and shown again), the framework must refetch through onMissingHTML. Invalid nesting, such as a <div> inside a <p>, is adopted as the browser parsed it, where React would rebuild it; a server-side nesting check could close that one.
  • Copies cost Next.js about 13% throughput. SSR gets copies of the stubbed elements, so it shares no object with the server, as the tee promises. Handing over the server's own elements is a one-line change that recovers the 13%; whether that rule can be relaxed is a question for the tee's design.
  • A check in React's child reconciler. Keeping stubs on later full payloads adds a host config function and a check at the two places the reconciler replaces a child of a different type, gated by the flag and run only on stubs. Without it, the first router.refresh() on the table page rebuilds 1,044 nodes.
  • HTML snapshots. While a router cache holds a page, each stubbed region keeps a string snapshot of its HTML, so Back restores it without a request. That uses less memory than the element tree it replaces: 75 DOM nodes kept after leaving the table page, against 256.
  • Preload links hoisted into <head> can differ from the feature off; the resources that matter are the same.

A path into React

  1. Land the Flight tee (react/react#38313 and its stack). HTML-first needs nothing else from upstream.
  2. Land HTML-first behind enableFlightHTMLFirst (PR #28): stubbing in Flight, the stub in the client, the reconciler check, and the htmlFirst option on the webpack and Turbopack server entries. Off by default; the option is ignored without the flag.
  3. Optionally, patch changed content in place (PR #31), so a refresh with different static content updates the DOM instead of rebuilding the element.
  4. Frameworks opt in on their HTML render: create a tee, pass the promise, settle it when Fizz is done, and pass onMissingHTML. The Next.js and Waku patches are working examples.

A version on top of Ledgers is kept up to date as well (PR #30).

Alternative considered: a process-global registry (PR #24)

The first implementation (PR #24) needs no tee. Flight puts the stubbed elements in a map on globalThis, and the first in-process createFrom* that reads the stream's id claims them. In November 19 measurements it reached the same byte savings (−42.8% gzip) and 3.5× Next.js throughput on the table page. It was set aside because:

  • it keeps rows in global state until a claim, an abort or garbage collection, and needed a FinalizationRegistry and random ids to stay safe;
  • it guesses with timers when SSR is done, where the tee version is told;
  • it pins a Fizz internal so late hints reach the HTML;
  • SSR still parses the whole payload, so pages that keep Client Component props gain less (Next.js 1.06×, against 1.19× with the tee).
  • it stubs the element a Client Component receives as children, so components that inspect it break: an asChild slot (React.Children.only) throws during SSR, and a list that filters its children by type hydrates with an error and renders empty. It also has no size minimum, so a page of 4,000 tiny elements gets 17% larger instead of smaller. The tee version handles all three.

Its numbers predate the November 23 rework of the tee version and were not measured again. Its pages stay online as the "registry" links on the examples index: the 41 original pages from November 19, plus three of the new ones (children inspection, suspending Client Component, tiny elements) built from its current head, ffeae9849d. The asChild page can't be built with it.
