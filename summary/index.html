HTML-first React: results

On first load, a React Server Components page sends its static markup twice. It goes once as HTML, so the browser can paint, and again inside the Flight payload that the browser uses to hydrate. For content that never changes on the client, the second copy is wasted bytes and server time.

HTML-first Flight, behind a new React flag enableFlightHTMLFirst, leaves that content out of the second copy. It now has two implementations that differ only in how SSR gets the content it still needs. The registry version (PR #24) passes it through a process-global registry. The tee version (PR #28) builds on Andrew Clark's Flight tee (react/react#38313), which lets SSR read the render without parsing it.

Both cut the gzipped download by 43% across 41 test pages and pass Next.js's own end-to-end suites. On a 1000-row table they tie, at about 3.4× Next.js's throughput. On a page that keeps Client Component props, the tee is faster: 1.29× against 1.06× on Next.js and about 1.5× against 1.1× on Waku. The tee version also drops the global registry and a Fizz workaround. Reviewers should look most closely at one check both add to React's child reconciler and at what the tee version changes.

Two implementations

Both versions stub the same markup, write the same bytes apart from a few dozen per page, and behave the same in the browser. They differ on the server, in how SSR gets the elements Flight left out of the bytes.

The tee version needed one scheduling change. Flight writes a row that's too large for one chunk as a chain of tasks, one per macrotask, and SSR rendered between them and suspended on each piece. With a tee attached, a pass now runs the tasks it made ready before it yields. This is the first item on the "Later" list of react/react#38313.

How it works

Flight writes a small stub in place of static host markup in the payload the browser receives. The browser adopts the matching DOM that the HTML already contains. SSR still needs the real content to write that HTML, so Flight hands it over: through the internal registry in the registry version, or through the tee in the tee version.

Markup qualifies when it is plain output of a Server Component in a position React renders in place:

  • children of host elements, Fragments and Suspense boundaries
  • children of Client Components, such as layouts and slots
  • plain data around elements, such as a root element map ({page, layout}) or a framework's route tree

Client Components are never stubbed. Neither are props other than children, because the client can render those later with no server DOM behind them. Forms, inputs, images, SVG, head elements and lone void elements such as <hr> are never stubbed either.

The framework asks only on the Flight render that feeds HTML SSR. Navigation, refetch and action responses stay full payloads. React can't tell where a stream is going, because the bytes are the same either way, but frameworks can: Waku serves RSC requests under an RSC/ URL prefix, and Next.js sends an RSC: 1 header.

What a stub does in the browser

This is the same in both versions.

  • During hydration, it adopts the server DOM.
  • Content SSR never rendered, such as the children of a closed modal or a hidden tab panel, arrives at the end of the stream as "late rows". The stub renders it when it mounts, with no extra request.
  • When it mounts again, for example after Back navigation, it rebuilds from a snapshot of the HTML it adopted, without inline event handler attributes.
  • When a later full payload arrives, from a refresh or a server action, React keeps the stub and its DOM if the new element renders the same DOM. If the content changed, React patches the DOM in place.
  • If content is still missing, for example after an error makes a boundary render on the client, React calls the framework's onMissingHTML callback, and the framework refetches the page.

Next.js

Next.js 16.4.6 needs a patch for each version. The registry version is about 165 lines on branch html-first/16.4. The tee version adds 82 lines and removes 12 on top of it, in three files, on branch html-first/16.4-tee. You turn either on with experimental.htmlFirstFlight: true in next.config.js. It's off by default. With it on:

  • Dynamic pages and PPR resumes ask on the HTML render. The tee version creates a tee there and reads SSR from it. RSC requests, such as navigation, refresh and actions, still get full payloads.
  • Prerendered pages keep their stored payload complete for navigations and prefetches. The copy inlined into the HTML is that payload decoded and encoded again with static markup left out. No Server Component runs twice.
  • Cache Components with cached navigations leave it out too, and the client cache's decode of the initial payload gets the same recovery callback as hydration.
  • Recovery through onMissingHTML refetches only the current route and keeps Next.js's client caches.

The test page is the same 1000-row table as on Waku, measured the same way. All three setups ran in the same rounds. The tee figures come from the exact Next.js and React tarballs in the html-first-flight-tee-189973d release.

Correctness

  • Next.js end-to-end tests: 52 of Next.js's own suites, run in production mode with Turbopack, pass in both versions. They cover the app router, navigation, the back/forward and client caches, parallel and intercepted routes, server actions, static generation and ISR, error and not-found pages, metadata, Cache Components and PPR. React is vendored the way Next.js ships it: the canary build in its stable slots and the experimental build in its experimental slots.
    • Registry: 871 tests passed with none failing.
    • Tee: the run on the release files took place on an overloaded machine. Three suites timed out in setup, and each passed three reruns in a row, 302 tests each time.
    • With the option off, rsc-basic, app-action and navigation pass 172 tests in both.
  • Next.js demo pages in Chromium: in both versions the hydrated DOM matches the baseline, counters respond, and client navigation and Back make the same requests as the baseline. The modal shows its content with no extra request.
  • 41 test pages: each page is loaded in the baseline, registry and tee setups, in Chromium 139, Firefox 157 and WebKit 18.4. The check compares the hydrated DOM, the DOM after interaction and the DOM after a client navigation to a full payload. It fails on any console or hydration error. All 41 pass in all three browsers for both versions. The comparison normalizes style spacing, zero-length CSS units and attribute order.
  • Waku: in both versions the page hydrates, its counters respond, it logs no errors, and a client navigation renders all 1000 rows.
  • React's own tests: on the tee branch, the full suite (334 test files, on experimental and stable) has no failures that don't also happen on flight-value-path alone. The HTML-first and Flight suites pass on experimental, stable, production and www-modern.

Trade-offs and limits

  • Reconciler check (both versions). Keeping stubs on later full payloads adds a host config function, instanceMatchesStaticElement, and a check at the two places React's child reconciler replaces a child of a different type. It's about 40 lines, gated by the flag, and it only runs on stubs. Without it, the first refresh on the table page takes 46 ms of main thread and rebuilds 1,044 nodes. With it, the refresh takes about the baseline's time and changes no DOM. Two ways to avoid touching the reconciler were tested and both rebuilt the DOM: a stub rendered as a host element of the same tag, and a stub rendered as a dehydrated Suspense boundary.
  • HTML snapshots (both versions). While Next.js's router cache holds a page, each stubbed region keeps a string snapshot of its HTML, so Back can restore it without a request. This uses less memory than the baseline, which keeps the full element tree for the same page: 75 DOM nodes remain after leaving the table page, against 256. Keeping the adopted nodes instead held about 14,000 detached nodes, and keeping nothing made Back refetch the route.
  • The tee version depends on the tee. It needs react/react#38313 to land, and enableFlightTee on in the channel a framework uses. A framework that doesn't create a tee gets no stubbing.
  • Weak promises (tee version). Through the tee, SSR sees a weak promise's placeholder value instead of staying pending, which differs from parsing the bytes. Nothing in Waku or Next.js reads one during SSR today. This belongs to the tee itself, not to HTML-first.
  • Global registry (registry version). Rows live on globalThis until a claim, an abort or garbage collection. The hardening added to PR #24 makes the :Q ids random and keys the store by a symbol. The tee version has no registry. It keeps the random :Q id, which the browser uses to share adopted nodes between decodes.
  • Recovery callback. Frameworks should still pass onMissingHTML. Late rows cover content SSR never rendered, but a boundary that renders on the client after an error has no server DOM. Without the callback, the page reports an uncaught error that names the element.
  • Preload links hoisted into <head> can differ from the baseline. The resources that matter are the same.
  • Savings scale with static markup. Expect many real pages to look like the median page, not the largest cases.

Try it yourself

You need Node 22 and npm. The starter apps install prebuilt packages from a release, so nothing is cloned or built. They've been tested with npm run build and npm start, not npm run dev. These are experimental builds, not for production.

  • Tee: the html-first-flight-tee-189973d release has React 189973d24a, Next.js html-first/16.4-tee and Waku rsc-html-first-tee. These are the exact files the tee benchmarks and Next.js end-to-end tests ran against, and the release lists their SHA-256 sums.
  • Registry: the html-first-flight-85b3ce1 release has React 85b3ce11a6 from PR #24, Next.js html-first/16.4 and Waku rsc-html-first-optin.

Method
  • The baseline is the same React build with the React flag off, which gives the same output as React main.
  • Byte figures for the 41 pages were measured in one run with three builds: the baseline and the tee from React 679a7e8309, and the registry from a later PR #24 build attributed to 85b3ce11a6. The tee's only later change to the bytes is a random :Q id, about 12 bytes per stubbed page. Two Suspense-heavy pages vary slightly between renders in every setup.
  • Next.js and Waku figures use the tee release files: React 189973d24a (canary, flag forced on), Next.js 9f9de6041d and Waku a45b595a. The registry figures use the html-first-flight-231161c release. Every bench app installed its packages by path, and its lockfile integrity matched the files.
  • Load is autocannon with 16 connections for 10 s after a 10 s warm-up, over 5 rounds on one laptop. Server order rotates each round, and ratios are taken within each round against the baseline. The load average was 3.5–5.4 during the rounds, so treat small differences as noise. Next.js uses next start with Turbopack. Refresh cost is Chrome's main-thread script, layout and style time, median of 10.
  • Earlier published figures for the registry version (Next.js 2.79×, Waku 3.18× and 1.10×) came from an earlier machine session. The figures above were measured alongside the tee in the same rounds.
  • Browser checks used Chromium 139, Firefox 157 and WebKit 18.4 (Playwright builds already on the machine).
