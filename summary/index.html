HTML-first React: Results Summary

Bottom line. React Server Components pages send their content twice on first load. For the part of a page produced by server code, we can stop doing that. Our test pages get up to 68% smaller over the wire (48% on the 1000-row page), with byte counts that reproduced exactly on a fresh rerun. It only takes effect when a framework opts in; Waku (patched locally) shows -55% / -46% / -33% client gzip on three page shapes.

Byte counts were re-measured from scratch and reproduced to within 0.01% to 0.04%. Timing gains are small and noisy; the case rests on bytes. See risks and limits.

Recommendation: pursue the Flight HTML-first work with a framework opt-in, using Waku as the reference integration.

1. The problem

  • An RSC page is delivered as HTML (Fizz) so the browser can paint, plus an inlined copy of the same content in Flight format so React can hydrate. Static markup (inline CSS, JSON-LD, plain elements) rides along twice and is dead weight the second time.
  • Flight is 37% to 76% of the document on our stock test pages (Waku: 48% to 54%).

2. The proposal

The HTML is the source of truth on first load. Flight is for navigation and actions. All flags are default off; nothing changes unless a framework opts in.

  1. Host elision: static host elements rendered by server components are not repeated in the initial Flight payload.
  2. Payload dedupe: long repeated strings and reference paths are sent once.
  3. HTML-first: static <style> and JSON-LD blocks stay out of Flight, and in-process SSR hands the live nodes over instead of re-serialising them. (An earlier iteration also had unstable_pruneForBrowser, an author assertion that a client component's props are unneeded in the browser. Commit 6ed2e62d21 on PR #21 removed it; client components now always keep full props. The measurements below were taken before that removal, so the "pruned" Waku row reflects the removed variant.)

4. How much to trust the numbers

  • Bytes are exact. HTML, gzip and inlined-Flight sizes reproduced on a fresh rerun within 0.01% to 0.04%.
  • Timing is noisy. The machine was not fully quiet, and the same code drifted 20% to 50% between processes. Only within-process ratios are used; cross-build throughput comparisons are left out as unreliable.
  • Hydration gain is small. 141.6 to 132.3 ms (-6.6%, about 9 ms, versus about 16 ms in the first run); the distributions overlap, so treat it as a small improvement, not a solid one.
  • Server render ratio reproduced (-17% to -20% vs -24%), but absolute milliseconds were 1.2x to 1.8x higher than the first run.
  • Waku was not re-run. Single sample per cell, bytes only, no timing.
  • Node 26, Chrome 157 only. No Firefox or WebKit.

5. Risks and limits

  • Client-component props are the floor. Only server-component output is elided; client components keep full props (the 1000-row client-row page only gets dedupe, -7% gzip).
  • Elision is static-only. Anything with a client component inside keeps its host skeleton.
  • Framework opt-in is mandatory. Flags alone change under 1% (Waku measured +0.06% to -0.6%).
  • Navigation still gets full Flight, and an elided region remounts on the first client navigation. Static prerendered pages are unaffected.
  • Dedupe reverses an upstream protocol decision and needs React maintainer sign-off.
  • Pruning was an author assertion (wrong means inert UI). It has been dropped from the current PR for that reason.
  • Chrome only. No Firefox or WebKit runs. Nothing is merged upstream.

6. Decisions and next steps

  1. Recommended: continue the Flight HTML-first stack (PRs #12 to #15, #21) and agree a framework opt-in contract, with Waku as the reference integration. Turn the local Waku patch into a proposal for Waku maintainers.
  2. Get maintainer feedback on payload dedupe, since it changes a protocol decision.
  3. Before any rollout: re-run Waku with timing, and test Firefox and WebKit.
