HTML-first React: Results Summary

Short version. When a React Server Components page loads, it sends its content to the browser twice. We found a way to skip the second copy for the parts the server renders. On our test pages that makes the download up to 68% smaller, and the server can handle up to 1.85 times as many requests. It only works if the framework turns it on, and we got it working in Waku with a small local patch.

What I'd do: keep going with this, and use Waku as the first real framework to build it into.

The problem

A server-rendered React page arrives in two forms at once. One is plain HTML, so the browser can show something right away. The other is an inlined copy in a format called Flight, which React uses to wake the page up in the browser (that step is called hydration).

For anything static, like inline CSS, structured data or plain markup, the second copy is dead weight. On our test pages Flight was 37% to 76% of the whole document. In Waku it was 48% to 54%.

The idea

Treat the HTML as the truth on first load. Use Flight only for navigation and actions after that. Nothing changes unless a framework asks for it, because every flag is off by default. There are three pieces:

  1. Host elision. "Elision" just means leaving something out. Plain elements (div, table, td) that a server component renders are left out of the first Flight payload, since the HTML already has them.
  2. Payload dedupe. Long strings and paths that repeat get sent once and referenced after that.
  3. HTML-first. Static CSS and JSON-LD blocks stay out of Flight too. When the server renders and sends HTML in the same process, it hands React the live nodes instead of re-serialising them.

One thing we dropped: an earlier version had unstable_pruneForBrowser, where the author promised a client component's props weren't needed in the browser. If the author got it wrong, the UI went dead. Commit 6ed2e62d21 on PR #21 removed it. Client components now always keep their full props. The measurements below were taken just before that removal, so the Waku "pruned" row is from the version we deleted.

Where it helps: content-heavy pages, where the server does about half the CPU work per request and sends 76% fewer bytes. The 1000-row page gets a smaller boost, mostly when rows are handed over live. Where it doesn't: client-component rows. We saw no real change there. Where it hurts: nowhere that we could measure. With the flags on but html-first not in use, the page ran at 0.98x, which is noise.

One small oddity: on the content-heavy page, adding dedupe on top of elision was a bit slower (1.64x vs 1.85x, and it repeated every round). That page has almost nothing for dedupe to remove, so it's pure overhead there. And even the best version is still well short of plain HTML, which served 1.7x to 5.7x as many requests. Some serialisation cost is left.

How much to trust this: I ran everything on a laptop that had other apps open, so treat the absolute numbers loosely. The comparisons are fair, though. All variants ran side by side in the same rounds, 7 rounds of 15 seconds each, and the host-heavy and 1000-row results varied by only 1% to 3% round to round. The client-row table was much noisier (about 20% spread), so "no change" is the most I'd say there. Servers ran on Node 22.9.

What we're sure of, and what we're not

  • Sure: the byte counts. We re-measured from scratch and they matched the first run to within 0.01% to 0.04%.
  • Fairly sure: the server throughput gains on content-heavy pages. They're large next to the noise.
  • Less sure: speed in the browser. Hydration got faster, 141.6 ms to 132.3 ms (about 6%), but the two sets of runs overlap, so I'd call it a small improvement at best. It was about 16 ms in the first run.
  • Timing is noisy: the same code ran 20% to 50% differently between separate processes on this machine. That's why we only compare things measured side by side.
  • Not tested: Waku speed (we only checked bytes), and anything other than Chrome. No Firefox or Safari.

Risks and limits

  • Client components set the floor. Only what server components render can be left out. Client components keep all their props.
  • Static only. A section with a client component inside keeps its outer skeleton.
  • The framework must opt in. Flags alone change under 1%.
  • Navigation is unchanged. Clicking to another page still gets the full Flight payload, and a trimmed section is rebuilt from scratch on the first navigation. Pages built ahead of time (static prerender) aren't affected.
  • Dedupe reverses an upstream decision. The React maintainers chose not to do this in the protocol, so they need to agree.
  • Chrome only so far, and nothing is merged upstream.

What I'd ask for

  1. Keep building the Flight HTML-first stack (PRs #12 to #15 and #21), and agree how a framework opts in. Use Waku as the first real integration and turn the local patch into a proposal for its maintainers.
  2. Ask the React maintainers about dedupe before investing more, since it changes a protocol choice.
  3. Before any rollout, measure Waku's timing and test Firefox and Safari.

Method and environment
  • Apple M3, 16 GB, macOS 26.6.2. Chrome 157.0.8103.39, headless, Chromium only. Byte counts and browser tests ran on Node 26.13; the throughput test ran on Node 22.9.
  • Flight: branch rsc/5-html-first-flight at 1930da7cf8, four production builds (flags off, elision, elision+dedupe, all). Flags are compile-time, so each is its own build.
  • Test page: 244 KB inline CSS, 143 KB JSON-LD, 1000-row table, every 100th row interactive. Hydration adopted the same DOM nodes (1000/1000), with no console problems.
  • Throughput: four servers side by side, one process each, with a separate load-generator process. 10 s warm-up, then 7 rounds of 15 s at 16 connections, with run order alternating each round. Ratios are per round against today's build. Latency at 1 connection and p99 are in the raw results. Zero request errors. Other apps (Task Manager, T3 Code) were using 20% to 50% of a core during the run.
  • Byte counts are deterministic apart from 0.01% to 0.03% jitter. Browser and render timings drifted 20% to 50% across separate processes, so only same-run ratios are used.
  • Waku numbers come from an earlier measurement: one sample per cell, bytes only.
  • Not measured: Firefox, WebKit, Waku timing.
