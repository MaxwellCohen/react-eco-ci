HTML-first React: results

On first load, a React Server Components page sends its static markup twice. It goes once as HTML, so the browser can paint, and again inside the Flight payload that the browser uses to hydrate. For content that never changes on the client, the second copy is wasted bytes and server time.

HTML-first Flight, behind a new React flag enableFlightHTMLFirst, leaves that content out of the second copy. Across 41 test pages it cuts the gzipped download by 43%. On a 1000-row table page, throughput rises 3.2× on Waku and 2.8× on Next.js 16.4. Next.js's own end-to-end suites pass with no failures. The code is PR #24. Reviewers should look most closely at one check it adds to React's child reconciler.

How it works

In the HTML-first setup, Flight writes a small stub in place of static host markup in the payload the browser receives. The browser adopts the matching DOM that the HTML already contains. SSR still needs the real content to write that HTML, so Flight hands it over through an internal registry.

Markup qualifies when it is plain output of a Server Component in a position React renders in place:

  • children of host elements, Fragments and Suspense boundaries
  • children of Client Components, such as layouts and slots
  • plain data around elements, such as a root element map ({page, layout}) or a framework's route tree

Client Components are never stubbed. Neither are props other than children, because the client can render those later with no server DOM behind them. Forms, inputs, images, SVG, head elements and lone void elements such as <hr> are never stubbed either.

The React flag alone doesn't change any output. The framework also has to pass htmlFirst: true, and only on the Flight render that feeds HTML SSR. Navigation, refetch and action responses stay full payloads. React can't tell where a stream is going, because the bytes are the same either way, but frameworks can: Waku serves RSC requests under an RSC/ URL prefix, and Next.js sends an RSC: 1 header.

What a stub does in the browser

  • During hydration, it adopts the server DOM.
  • Content SSR never rendered, such as the children of a closed modal, arrives at the end of the stream as "late rows". The stub renders it when it mounts, with no extra request. SSR marks the rows it renders with a lazy node, so marking costs nothing measurable.
  • When it mounts again, for example after Back navigation, it rebuilds from a snapshot of the HTML it adopted.
  • When a later full payload arrives, from a refresh or a server action, React keeps the stub and its DOM if the new element renders the same DOM. If the content changed, React patches the DOM in place.
  • If content is still missing, for example after an error makes a boundary render on the client, React calls the framework's onMissingHTML callback, and the framework refetches the page.

Throughput on Waku

The test page is a 1000-row table rendered by Server Components, plus inline CSS and JSON-LD. Waku was picked because it's easy to patch and has good RSC support. The feature doesn't depend on it. The Waku patch is what asks for it, in two parts: the HTML render passes htmlFirst: true, and the root refetches the initial payload when React reports that stubbed content is missing.

Next.js

Next.js 16.4.6 needs a patch of about 165 lines, on branch html-first/16.4. You turn it on with experimental.htmlFirstFlight: true in next.config.js. It's off by default. With it off, the patched Next.js doesn't ask for HTML-first output, so it behaves like unpatched Next.js. With it on:

  • Dynamic pages and PPR resumes pass htmlFirst: true on the HTML render. RSC requests, such as navigation, refresh and actions, still get full payloads.
  • Prerendered pages keep their stored payload complete for navigations and prefetches. The copy inlined into the HTML is that payload decoded and encoded again with static markup left out, the same way Next.js already re-encodes it for segment prefetches. No Server Component runs twice.
  • Cache Components with cached navigations leave it out too. Next.js counts the stage byte lengths on that stream, and the client cache's decode of the initial payload gets the same recovery callback as hydration.
  • Recovery through onMissingHTML refetches only the current route and keeps Next.js's client caches.

The test page is the same 1000-row table as on Waku, measured the same way. A second copy of it is prerendered at build time.

Correctness

  • Next.js end-to-end tests: 52 of Next.js's own suites, run in production mode with Turbopack in the HTML-first setup, pass 871 tests with none failing. They cover the app router, navigation, the back/forward and client caches, parallel and intercepted routes, server actions, static generation and ISR, error and not-found pages, metadata, Cache Components and PPR. React is vendored the way Next.js ships it: the canary build in its stable slots and the experimental build in its experimental slots.
  • Next.js demo pages in Chromium: the hydrated DOM matches the baseline, counters respond, and client navigation and Back make the same requests as the baseline. The modal shows its content with no extra request.
  • 41 test pages: each page is loaded in Chromium in the baseline and HTML-first setups. The check compares the hydrated DOM, the DOM after interaction and the DOM after a client navigation to a full payload. It fails on any console or hydration error. All 41 pass at 126b0905e5. The comparison normalizes style spacing, zero-length CSS units and attribute order.
  • Waku: the page hydrates, its counters respond, it logs no errors, and a client navigation renders all 1000 rows.
  • Not run on the final commit: Firefox and WebKit passed on earlier commits only. The CI report on Linux covers 10 page variants at an earlier commit (report).

Trade-offs and limits

  • Reconciler check. Keeping stubs on later full payloads adds a host config function, instanceMatchesStaticElement, and a check at the two places React's child reconciler replaces a child of a different type. It's about 40 lines, gated by the flag, and it only runs on stubs. Without it, the first refresh on the table page takes 46 ms of main thread and rebuilds 1,044 nodes. With it, the refresh takes 19 ms and changes no DOM, against 18 ms for the baseline. Two ways to avoid touching the reconciler were tested and both rebuilt the DOM: a stub rendered as a host element of the same tag, and a stub rendered as a dehydrated Suspense boundary.
  • HTML snapshots. While Next.js's router cache holds a page, each stubbed region keeps a string snapshot of its HTML, so Back can restore it without a request. This uses less memory than the baseline, which keeps the full element tree for the same page: 75 DOM nodes and 4.21 MB of JS heap remain after leaving the table page, against 256 nodes and 4.35 MB. Keeping the adopted nodes instead held about 14,000 detached nodes, and keeping nothing made Back refetch the route.
  • Recovery callback. Frameworks should still pass onMissingHTML. Late rows cover content SSR never rendered, but a boundary that renders on the client after an error has no server DOM. Without the callback, the page reports an uncaught error that names the element.
  • Preload links hoisted into <head> can differ from the baseline. The resources that matter are the same.
  • Savings scale with static markup. Expect many real pages to look like the median page, not the largest cases.

Try it yourself

You need Node 22 and npm. Both starter apps install prebuilt packages from the html-first-flight-231161c release, so nothing is cloned or built. The release has React 231161c38d with the React flag on, the patched Next.js 16.4.6 and the patched Waku. Both starters have been tested with npm run build and npm start, not npm run dev. These are experimental builds, not for production.

Next.js

npx degit MaxwellCohen/react-eco-ci/starters/next-html-first-flight next-html-first
cd next-html-first
npm install
npm run build
npm start            # http://localhost:3000
npm run measure      # in a second terminal

The starter's next.config.mjs sets experimental.htmlFirstFlight: true. npm run measure prints the size of /table, /static-table and /client-rows next to the baseline: Next.js 16.4.6 with the same React build and the React flag off. On /table it shows about 97% less inlined Flight and 49% less gzipped HTML. Open /modal and click the button: the static terms appear with no extra request. To use the packages in your own app, install the next, react and react-dom tarballs from the release, override react, react-dom and scheduler as the starter's package.json does, and set the config flag. The app must work on Next.js 16.4.

Waku

npx degit MaxwellCohen/react-eco-ci/starters/waku-html-first-flight waku-html-first
cd waku-html-first
npm install
npm run build
npm start            # http://localhost:8080
npm run measure      # in a second terminal

npm run measure prints the size of the two table pages next to the baseline numbers for the same pages. Open /table-host and view the source: the inlined Flight payload is small and contains $J stubs. To add the packages to your own Waku app, install the four tarballs from the release and override scheduler and react-is as well. The react-eco-ci README has the exact command and overrides. The app must work on Waku 1.0.0-rc.4.

Method

  • Byte figures for the 41 pages were measured at 5a400f9164 and repeated with the rules Next.js needed (cbf8821a69). Only fragments-arrays-keys changed, by 19 bytes. A few pages vary slightly between runs because of generated ids.
  • Waku figures use React 60d28f4ee6 and Waku 62e75f5f. Load is autocannon with 16 connections for 10 s after a 10 s warm-up, over 5 rounds on one laptop. Server order rotates each round, and ratios are taken within each round against the baseline.
  • Next.js figures use next start with Turbopack and the same load. The baseline is PR #24 with the React flag off, vendored into unpatched Next.js 16.4.6. Throughput uses React 604c7e5239, which includes late rows. Refresh cost is Chrome's main-thread script, layout and style time, median of 5. Memory is Chrome's DOM node count and JS heap after a forced garbage collection, median of 3. Later commits change only browser-side behavior and the Cache Components paths.
