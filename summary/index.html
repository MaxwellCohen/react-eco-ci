HTML-first React: results

An RSC page's first response sends its static markup twice: once as HTML and once inside the Flight payload that the browser uses to hydrate. The reference implementation, PR #24 (final version b248e1e4ae), adds a flag, enableFlightStaticHostElision, that leaves static Server Component output out of the browser's copy. Across 41 test pages it cuts the gzipped download by 43% and the inlined Flight payload by 79%. In a Waku page with a 1000-row server-rendered table it raises throughput 3.2×. The framework change needed is one option.

What it does

With the flag on, Flight does not put static host markup into the payload the browser receives. It writes a small stub, and the browser adopts the DOM that the HTML already contains. SSR still gets the full content, handed over through an internal registry, so the HTML is complete.

The static markup that qualifies is plain output of Server Components in places where React renders it in place: host element children, Suspense children, Client Component children, and the entries of a root element map such as {page, layout}. Client Components are never elided, and neither are props other than children, since the client can render those later with no server DOM behind them. Forms, inputs, images, SVG and head elements are never elided either.

Nothing is elided unless the framework asks. It passes elideStaticHosts: true on the Flight render that feeds HTML SSR. Navigation, refetch and action responses do not pass it, so they are ordinary full payloads. React cannot tell where a stream is going, because the bytes are the same either way, but frameworks already can: Waku serves RSC requests under an RSC/ URL prefix, and Next.js sends an RSC: 1 header.

Throughput: Waku

The test is a Waku page with a 1000-row table rendered by Server Components, plus inline CSS and JSON-LD. Waku was used because it is easy to patch and has good RSC support; the feature does not depend on it. Results are medians over 5 rounds on one laptop, with the order of the servers rotated each round. The patch is one line: the HTML render passes elideStaticHosts: true.

Correctness

The 41 pages are loaded in real Chromium with and without the flag, and each check compares the hydrated DOM, the DOM after interaction, and the DOM after a client navigation to a full payload. It also fails on any console error or hydration error. All 41 pass at 31b26561f1. The comparison normalizes style spacing, zero-length CSS units and attribute order. Firefox and WebKit passed at earlier commits and have not been run on this one. The Waku page hydrates, its counters respond, there are no console errors, and navigation renders all 1000 rows.

On a client navigation the full payload has real elements where the stubs were, so React creates fresh DOM for those regions instead of reusing the old DOM, whose content may not match the new page. Client components keep their state.

Limits

  • If an elided region is rendered on the client with no server DOM behind it (a modal or client-only wrapper that mounts after hydration, or a boundary that client-renders after an error), React cannot recreate the content. The framework has to pass onElidedContentMissing and refetch a full payload. Without it the page reports an uncaught error.
  • Rows that nothing in-process consumes are released only when the request is aborted, so a response that is only ever sent to a browser, with the option on, keeps its rows in memory.
  • Preload links hoisted into <head> can differ from stock; the resources that matter are the same.
  • The savings depend on how much static server markup a page has. Many real pages will land near the median, not the large cases.

Method
  • Baseline is the same React build with the flag off. Both builds come from the PR #24 branch, rebased onto facebook/react main.
  • Byte numbers are deterministic for most pages; a few pages vary slightly between runs because of generated ids, so the last digits can differ on a rerun.
  • Render-time numbers (not shown here) come from interleaved in-process renders and are noisier than the byte numbers.
  • Waku: autocannon with 16 connections for 10 s after a 10 s warm-up, 5 rounds, ratios taken within each round against stock. Chromium 156 for the browser checks.
