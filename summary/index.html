HTML-first React: Results Summary

Short version. An RSC first load sends the same static content twice: Fizz HTML to paint, and an inlined Flight payload to hydrate. With one experimental flag and a framework opt-in, static Server Component host markup in host position — including Suspense children and Client Component children — is left out of that Flight copy and adopted from the HTML. Across a 41-page corpus (before children elision) gzip was 42% smaller overall; children elision restores the common provider/layout case that had dropped to zero. Dedupe is out of this proposal.

The problem

A server-rendered RSC page arrives as HTML (paint) plus an inlined Flight payload (hydrate). For static server markup the second copy is dead weight. Earlier measurements put inlined Flight at roughly half the document on content-heavy pages.

The idea (one flag)

One compile-time flag: enableFlightHtmlFirst. When a framework opts in:

  1. Static host elements in host position are withheld from the browser Flight stream: Server Component output, children of host tags and Suspense, and children of Client Components (layouts / composition slots).
  2. Non-children props (Tabs panels, Suspense fallback, …) stay in the payload.
  3. SSR receives withheld rows via onElidedRow / onElidedValue; the browser adopts server DOM for stubs on hydration.
  4. If a stub mounts without server DOM (modal, ClientOnly, or a boundary/root that client-renders), it suspends and calls optional onElidedContentMissing so the framework can re-render from a full payload. Without it, the page stays non-blank.

Not in this proposal: a separate host-elision-only mode, payload dedupe (draft #15), and the lazy client parser (draft #14).

41-page corpus (after correctness fixes + Suspense)

Each page is rendered with flags off and with HTML-first on, hydrated in a real browser, interacted with, and compared after a full-Flight navigation. Builds include the position fix and Suspense support.

What we're sure of, and what we're not

  • Sure: byte counts on the corpus are deterministic (aside from a few Suspense pages with timing-dependent HTML). Cross-browser correctness after the fixes.
  • Fairly sure: Waku host-row byte and throughput gains with the opt-in patch.
  • Trade-offs to name honestly: recovery and the first client navigation remount elided regions (plus a network round trip when a stub mounts without server DOM — modals, ClientOnly). That cost sits on interaction/error paths, not on the common always-rendered layout case.
  • Less sure / noisy: absolute render timings on a shared laptop; treat ratios as rough.

Risks and limits

  • Client components and non-host-position trees set the floor.
  • Suspense fallbacks stay un-elided.
  • The framework must opt in; flags alone do almost nothing.
  • Maintainers may still want a narrower first slice (e.g. only <style> / JSON-LD).
