HTML-first React: results

On first load, an RSC page sends its static markup twice: as HTML, so the browser can paint, and again inside the Flight payload the browser inlines to hydrate. For content that never changes on the client, the second copy is wasted bandwidth, and it costs the server time to produce.

This experiment adds a flag that leaves that content out of the second copy. Across 41 test pages it cuts the gzipped download by 43%. On a Waku page with a 1000-row table rendered by Server Components it raises throughput 3.2×, and on Next.js 16.4 the same page gets 2.7× with four more changes to React's rules. A framework turns it on with one server option and, for full safety, one client callback. The code is PR #24, a reference implementation (final version b22ca3d704).

How it works

With enableFlightStaticHostElision on, Flight does not write static host markup into the payload the browser receives. It writes a small stub instead, and the browser adopts the DOM that the HTML already contains. SSR still needs the real content to write that HTML, so Flight hands it over through an internal registry.

Markup qualifies when it is plain output of a Server Component in a place React renders in place:

  • children of host elements and of Suspense boundaries,
  • children of Client Components (layouts, slots),
  • the entries of a root element map such as {page, layout}.

Client Components are never elided. Neither are props other than children, because the client can render those later with no server DOM behind them, nor forms, inputs, images, SVG or head elements.

The feature is opt-in per request. The framework passes elideStaticHosts: true on the Flight render that feeds HTML SSR, and leaves it off everywhere else, so navigation, refetch and action responses stay ordinary full payloads. React cannot tell where a stream is going, because the bytes are identical either way. Frameworks can: Waku serves RSC requests under an RSC/ URL prefix, and Next.js sends an RSC: 1 header.

Throughput on Waku

The test page is a 1000-row table rendered by Server Components, plus inline CSS and JSON-LD. Waku was chosen because it is easy to patch and has good RSC support; the feature does not depend on it. The patch has two parts: the HTML render passes elideStaticHosts: true, and the root refetches the initial payload when React reports that elided content is needed. Figures are medians over 5 rounds on one laptop, with the order of the servers rotated each round.

Next.js

Next.js 16.4.6 needs a small patch, about 100 lines in four files, on branch html-first/16.4 (e21f6ffa1b):

  • Dynamic pages. The HTML render passes elideStaticHosts: true to the Flight render that feeds SSR, including PPR resumes, whose static shell is already in the prerendered HTML. RSC requests (navigation, refresh, actions) still get full payloads.
  • Static pages. A prerendered page's payload is also stored for navigations and prefetches, so it has to stay complete. It is rendered once as before; the copy inlined into the HTML is that payload decoded and encoded again with elision, the same way Next already re-encodes it for segment prefetches. No Server Component runs twice. Fully static Cache Components pages are handled the same way when cached navigations are off.
  • Cached navigations. With cacheComponents, the staged render behind cached navigations passes the option too; its stage byte lengths are counted on the elided stream. The client cache's decode of the initial payload gets the same recovery callback as hydration.
  • Recovery. Hydration passes onElidedContentMissing, which refetches only the current route and keeps Next's client caches.

With PR #24 as it was, Next elided nothing. PR #24 now includes seven more React changes (diff), each with a test that fails without it:

  • Fragments. Next wraps each route segment in a keyed <Fragment>. Its children render in place, like those of Suspense, but were treated as a prop React might render later.
  • Plain data. Next keeps segment output in a route tree ({t: {d: {r}}, c: Map}). Plain objects, arrays and Maps now keep the position they are in; only an element's non-children props drop out, as before. Before, this held only for data in the root task, not in outlined ones such as Maps.
  • Void elements. A lone <hr> was elided, and its stub broke hydration (React error #137). Void elements are no longer elided on their own; they still are inside a static parent.
  • Mounting again. On back and forward navigation Next renders the cached initial payload again, with no server DOM behind it. A stub now keeps the DOM node it adopted and moves its content into the new element, instead of asking for the full payload.
  • Node web streams. The Turbopack and unbundled Node builds dropped the option in renderToReadableStream.
  • Late rows. Static content SSR never rendered (children of a closed modal, a client-only wrapper) used to cost a request when it mounted. SSR now marks the rows it renders, with a lazy node that Fizz resolves only where it renders, and the server sends the rest at the end of the stream under the stubs' ids. A first version marked rows with a component and cut throughput from 2.64× to 2.51×; the lazy node costs nothing measurable. If SSR never claims the rows, or the render aborts, the stream closes without them.
  • Several decodes. Next decodes part of the initial payload again for its client cache. Stubs from every decode of the same payload now share the node hydration adopted, through a map keyed by the payload's id and held weakly.

A stricter alternative to the plain-data rule was tried: the framework names the data keys it renders in place (elideStaticHosts: {inPlace: ['t', 'd', 'r', 'c']}, React, Next.js). It gave the same bytes, throughput and test results but adds API, so it was not kept. The changes leave the 41 test pages as they were, except fragments-arrays-keys, which gets 19 bytes smaller; all 41 still pass in Chromium, and Waku's bytes are unchanged.

Next's own end-to-end tests were run against the patched Next with PR #24 vendored, in production mode with Turbopack: 52 suites, including Cache Components and PPR, covering the app router, navigation, back/forward cache, client cache, parallel and intercepted routes, server actions, static generation and ISR, generateStaticParams, fetch deduping, error and not-found pages, metadata and root layouts. 867 tests pass, and 2 more pass on rerun. The 2 failures check React's version string and fail the same way with elision switched off. An earlier set of the core suites also passed with webpack and in next dev. In Chromium the hydrated DOM matches stock on every demo page, counters respond, client navigation and Back make the same requests as stock, and the modal shows its content with no extra request.

Correctness

The 41 pages are loaded in Chromium with and without the flag. For each one the check compares the hydrated DOM, the DOM after interaction, and the DOM after a client navigation to a full payload, and it fails on any console or hydration error. All 41 pass at 5a400f9164. The comparison normalizes style spacing, zero-length CSS units and attribute order. Firefox and WebKit passed on earlier commits but have not been run on this one. The Waku page hydrates, its counters respond, it logs no errors, and a client navigation renders all 1000 rows.

The same kind of check also runs in CI on Linux, with the flag off and on, in real Chromium. The latest CI report covers 10 page variants at df356153a6: every one adopts 1000 of 1000 rows from the server HTML, logs no console problems and no recoverable hydration errors, and navigates correctly.

On a client navigation the full payload contains real elements where the stubs were. React builds fresh DOM for those regions rather than reusing the old DOM, whose content may not match the new page. Client components keep their state.

Limits

  • If an elided region is rendered on the client with no server DOM behind it (a modal or client-only wrapper that mounts after hydration, or a boundary that client-renders after an error), React cannot recreate the content. The framework must pass onElidedContentMissing and refetch a full payload. The Waku patch does, and a modal that mounts its static children after a click then shows them as it does on stock. Without it the page reports an uncaught error that names the element.
  • Preload links hoisted into <head> can differ from stock. The resources that matter are the same.
  • Next.js: the first full payload a page receives after loading (a router.refresh(), a server action that revalidates, returning to a PPR page) swaps each stub for a real element of a different type, so React rebuilds that static DOM instead of keeping the server's: 1,044 nodes in about 50 ms on the table page, once per page load. Stock changes no DOM there. Client state is kept, and later updates diff normally. Avoiding it needs React to hydrate a subtree during an update, for example by treating stubs as dehydrated boundaries.
  • Next.js: each elided region keeps its detached DOM node while Next's router cache holds the payload, so that Back can restore it without a request. The memory is freed with the cache entry.
  • Next.js with cacheComponents and cached navigations: fully static pages keep the full inlined payload. Eliding them made Next's back/forward cache test fail (a page evicted and visited again rendered without its static content), and that path is not understood yet.
  • The savings scale with the amount of static server markup on a page. Expect many real pages to look like the median, not like the largest cases.

Try it yourself

You need Node 22 and npm. Nothing is cloned or built: the starter app installs a React build with the flag on and a Waku with the patch, both from a GitHub release.

npx degit MaxwellCohen/react-eco-ci/starters/waku-static-host-elision elision-demo
cd elision-demo
npm install
npm run build
npm start            # http://localhost:8080
npm run measure      # in a second terminal

npm run measure prints the size of the two table pages next to what stock React and stock Waku send for the same pages. Then open /table-host and view the source: the inlined Flight payload is small and contains $J stubs. Open /late-modal and click “open”: that content was not in the first payload, and appears because Waku refetches it. I have run npm run build and npm start, not npm run dev.

To add the packages to your own Waku app, install the four tarballs from the release and override scheduler and react-is as well; the exact command and overrides are in the react-eco-ci README. The app needs to work on Waku 1.0.0-rc.4, and these are experimental builds, not for production.

  • React part: branch rsc/html-first-one-flag at 5a400f9164 (PR #24), built with enableFlightStaticHostElision forced on.
  • Waku part: the patch against upstream Waku (branch rsc-html-first-optin): two small changes, in render.ts and client-runtime.tsx.
  • Packages and starter: release with the tarballs, the starter app.
  • Build them yourself: the README has the CI inputs for the react-build workflow and the local steps.

Method
  • The baseline is the same React build with the flag off. Both builds come from the PR #24 branch, rebased onto facebook/react main.
  • Byte figures and the Chromium check for the 41 pages were measured at 5a400f9164, and repeated with the rules Next.js needed (cbf8821a69): all 41 pass, and only fragments-arrays-keys changes, 19 bytes smaller. The Waku figures use React 60d28f4ee6 and Waku 62e75f5f.
  • Byte counts are deterministic for most pages. A few vary slightly between runs because of generated ids, so the last digits can change on a rerun.
  • Waku: autocannon with 16 connections for 10 s after a 10 s warm-up, 5 rounds, ratios taken within each round against stock. Chromium 156 for the browser checks.
  • Next.js: next start with Turbopack, Next.js 16.4.6, same load and rounds as Waku. Stock is PR #24 with the flag off, vendored into Next.js; throughput uses React with late rows (604c7e5239) and Next.js ff79c82d63, against the same build without late rows in the same run (2.65×); later commits only add the Cache Components paths and browser-side restore. End-to-end tests at the final commits: 52 suites, 867 passing, 2 that failed once and passed on two reruns each, and the 2 version-string failures. The Waku comparison used the same React builds as the throughput run.
