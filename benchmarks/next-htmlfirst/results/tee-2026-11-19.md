# HTML-first Flight on the Flight tee: Next.js 16.4.6, 2026-11-19

The Next.js patch was moved from React's in-process registry (React `231161c38d`) to the Flight tee (React PR #28, `679a7e8309`). Bytes, browser behaviour and e2e results match the registry version. Throughput is the same or slightly higher.

- Next.js: MaxwellCohen/next.js `html-first/16.4-tee` at `9f9de6041d`, one commit on top of `c19d05febc` (`html-first/16.4`). Still gated by `experimental.htmlFirstFlight` (default false).
- Tarball: `next-16.4.6-html-first-flight-tee.tgz` (scratchpad of session e78ade9f; see "Artifacts").
- Raw data: `tee-2026-11-19-main.json` (bytes, throughput rounds), `-extra.json` (prerendered/PPR/static bytes, stored payloads, DOM nodes and heap, cacheComponents browser check), `-refresh.json` (10 trials), `-check.json` (browser check), `-e2e.json`.
- Scripts: `../tee-round/` (`make-variant.sh`, `measure-extra.mjs`, `refresh.mjs`, `e2e.sh`, `e2e-suites-52.txt`), plus `../measure.mjs` and `../check.mjs` from the previous round.

## What changed in Next.js

3 files, +82 / −12.

- `use-flight-response.tsx`: `createFlightTee(nonce)` creates a tee with the SSR module map. `getFlightStream` also accepts `{ flightTee }` and reads it with `createFromTee`, cached per source like the stream path.
- `app-render.tsx` (`renderToStream`): the dynamic render, the PPR resume and the Cache Components cached-navigations render each create a tee before the render starts. They pass `{ htmlFirst: true, tee }` and give `<App>` `{ flightTee }` instead of a copy of the bytes. The byte stream is still inlined for the browser, and with cached navigations it is still counted for the stage byte lengths.
- `$$compiled.internal.d.ts`: `createTee`, `createFromTee`, `FlightTee`, and the `tee` server option.

Paths that stay on bytes, and what they get:

| Path | Before (registry) | Now (tee) |
|---|---|---|
| Dynamic render, PPR resume, cached-navigations render | `htmlFirst: true`; SSR claims the stubbed rows from the registry | Tee; SSR reads it, browser bytes are stubbed |
| Resume whose HTML is already complete (`DynamicState.DATA`) | `htmlFirst: true`; nobody claims the rows | No tee, so the payload is full. Nothing reads the tee there, and an unread tee holds the stream for late rows (up to 1 s). |
| Prerender: stored payload (`.rsc`, prefetch segments) | Full | Full: the prerender render has no `htmlFirst` |
| Prerender: inlined copy | Stored payload decoded and re-encoded with `htmlFirst: { onValue }` | Unchanged. This React still accepts `{ onValue }` without a tee, so the copy is stubbed. |
| Browser: client-cache decode of the initial payload, `onMissingHTML` recovery | Unchanged | Unchanged |
| Dev Cache Components staged render, error renders | No `htmlFirst` | No tee |

The stored payloads have no stubs in either version (static-table 680,761 B; Cache Components static page 105,831 B).

## Setup

- One machine (Node 26.13), one session. Three variants, each built from the same app sources with Turbopack (`next build`, then `next start`):
  - off: stock Next.js 16.4.6, the previous round's `off-stock` tarball.
  - registry: release `html-first-flight-231161c` (`next-16.4.6-html-first-flight.tgz`).
  - tee: this branch.
  - registry and tee set `experimental.htmlFirstFlight: true`.
- Apps:
  - The current react-eco-ci `templates/next` app: 1000-row table, client-rows, prerendered static-table, modal.
  - The previous round's Cache Components app: `/ppr` and `/static`, `cacheComponents: true`.
  - The template changed slightly since the published run, so off now inlines 765,387 B instead of 765,297 B.
- Throughput: `measure.mjs`. 16 connections, 10 s after a 10 s warm-up, 5 rounds. Each round rotates and alternates the variant order. Ratios are per round against off; the table shows the median and (min–max).
- Load average was 7–12 during the throughput rounds, because other sessions were running on the machine. Absolute requests/s are therefore lower than in the published run; same-round ratios correct for most of this. No request errors, timeouts or non-200 responses.

- Tee against registry, same round: table 0.97–1.22× (median 1.01), client-rows 1.05–1.29× (median 1.16).
  - On the stubbed table page the two are within noise.
  - The client-rows page has almost nothing to stub (1 stub). It still gains about 16–20%, which fits SSR reading the render through the tee instead of parsing its bytes again.
- The tee's /ppr and /modal payloads are about 47 B smaller than the registry's. The rest of the difference is build-specific chunk names and module IDs, plus the registry's `:q` claim row, which the tee build doesn't emit.
- Refresh: the 5-trial run in `-extra.json` was noisy (tee 19 / 17 ms, with outliers of 37 and 45 ms under load). It was re-run with 10 interleaved trials in `-refresh.json`, which is the row above. Ranges overlap for all three variants.

Browser checks in Chromium (`check.mjs` and `measure-extra.mjs`):
- The hydrated DOM is identical across off, registry and tee on /table, /client-rows, /modal, Cache Components /static and /ppr.
  - `domMatchesStock: false` for /table in `-check.json` is a harness artifact. `check.mjs` normalizes only the experimental React version string, and with that fixed the three DOMs are byte-identical.
- Counters respond on every page.
- Client navigation and Back work on every page, with the same RSC requests as off.
- The modal shows its 20 clauses after opening.
- Cache Components: navigation to /static and Back to /ppr render 1000 rows.
- No console errors or warnings.
- Known bug: `measure.mjs` waits for the URL `/client rows` (no path mapping), so its /table navigation check times out for all three variants, including off. `check.mjs` has the fix.

The same 52 suites as the published registry run (`all37.txt` + `cc-suites.txt` from that session, copied to `tee-round/e2e-suites-52.txt`). React is vendored the same way: canary build in Next's stable slots, experimental build in its experimental slots.

- Option on (default flipped to true): 870 passed, 1 failed, 251 skipped, 1,122 total. 49 suites passed, 1 failed, 2 skipped.
  - Failed: `searchparams-reuse-loading › With Middleware › should correctly return different RSC data for full prefetches with different searchParam values`. The test expected no RSC request for `?id=3` after a full prefetch, and saw one.
  - This is a flake, not the tee. The same test failed the same way on the registry build in that session's `final52.log`, then passed in its reruns. Here it passed 3 of 3 reruns with the option on.
  - It also only checks prefetch RSC requests, which never use `htmlFirst`.

## Notes and caveats

- The canary build needs `enableFlightTee`. In PR #28 it is `__EXPERIMENTAL__`, so the canary build provided for this run threw "createTee is not supported in this build of React". Next.js uses its stable (canary) slot unless an app opts into experimental React, so every dynamic page returned 500.
  - For these numbers React `679a7e8309` was rebuilt with `enableFlightHTMLFirst` and `enableFlightTee` both forced on, both channels, all bundle types.
  - Next.js on canary React needs the tee flag on in canary.
- The vendored React is not committed on the branch, the same as on `html-first/16.4`. The tarball contains it.
- The tarball was packed with `htmlFirstFlight: false`; turn it on with `experimental.htmlFirstFlight: true`.
