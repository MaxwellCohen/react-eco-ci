template for in streaming SSR: the case, and what is missing

React and Preact stream late Suspense content as hidden HTML plus a script that moves it into place. <template for> lets the browser do that move. This page sums up what we measured in both libraries, why the wire format is worth adopting, and which jobs still need script because the platform does not cover them.

Why adopt

  • Content streams in without script in browsers that support it.
  • 37–55% less main-thread time than React’s $RC at the same reveal policy.
  • Bytes, patch timing and correctness are level or better.
  • One standard wire format instead of one per library.

What is lacking

  • A native patch cannot be batched or delayed, so React has to switch native patching off when scripts run.
  • View transitions, SVG/MathML, style ordering and hydration state still need script.
  • Chromium only. Everything else needs a script fallback.
  • The React PR’s current head has not been benchmarked yet.

Why adopt

  1. It works before, and without, script. The browser applies a patch as it parses it. With a strict CSP that blocks the library’s inline scripts, the Preact test page still completed in Chromium; today’s format leaves every fallback on screen.
  2. It costs less main-thread time at React’s reveal policy. With reveals grouped in the same ~300 ms window React uses today, a small script helper applying <template for> content used 37% less at 60 boundaries, 53% less at 500 and 55% less at 2,000. Native apply used 39% and 48% less at 60 and 500.
  3. It does not cost bytes or time to content. Whole documents are 6–8% smaller raw and within about 1% after gzip from 500 boundaries up. Patch lag is statistically level at the same policy.
  4. It fixed real bugs in Preact. The <template for> PRs pass 26 of 26 DOM checks in three browsers. Preact main passes 23 (table rows, SVG and MathML fail).
  5. It is a platform format. Libraries that emit the same markers get faster as browsers do, and each gap closed in the platform is script a library can delete.

What is lacking

  • The native path is off whenever scripts run (React). To keep React’s reveal throttle without holding bytes on the server, the PR disarms native patching and applies in script. Native patching only happens with scripts disabled or blocked, and then it is unthrottled.
  • The PR head is unmeasured. Client-side batching landed after the benchmark runs. A rerun on that build, and a fresh $RP size, are still owed.
  • The React diff is not small. PR #25 is +2,650 / −33 across 33 files, behind a flag that is off in every build. Most of the runtime code covers the platform gaps below.
  • Chromium only. Firefox and WebKit need the script fallback, and a strict CSP without a nonce blocks it.
  • A MutationObserver polyfill is not a fallback at scale. It costs 2× classic at 500 boundaries and 6.7× at 2,000.
  • Thin evidence in places. One machine. Main-thread cost was measured in Chromium only, with hydration off. Not measured: slow CPUs, throttled networks, real wire compression, intermediate visual states.

Platform gaps: notes for web standards

Each item is something a streaming library needs that <template for> does not do natively, as observed in Chromium 156, with the script React or Preact uses instead. Formatted notes: platform gaps. Raw markdown to paste into an issue: platform-gaps.md.

1A patch cannot be held, batched or scheduled

Today
The browser applies a patch while parsing it. No attribute, event or API can delay it or group it with others.
Cost
React throttles reveals on purpose (~300 ms) so content does not pop in one boundary at a time. Without a client schedule, native apply is immediate and unthrottled. A server-side hold would batch, but it delays bytes, which React will not do.
Workaround
$RP() rewrites every <?start name> into a comment after the shell, so the browser has nothing to patch, then applies queued templates after the throttle.
Ask
A way to apply patches together: a group that commits at its end, a frame-aligned commit, or a cancellable event before apply.

2No signal that a patch was applied

Today
No event fires when a range is patched.
Cost
The library must mark the boundary complete and retry hydration at that moment.
Workaround
React’s client watches the markers with a MutationObserver. The server still sends a script after each flushed group.
Ask
A patch event that names the range.

3A native patch cannot join a view transition

Today
A native patch is a plain DOM change, outside startViewTransition, with no point at which to set per-element transition names.
Workaround
When the page uses <ViewTransition>, the script applies the batch inside one transition, as $RC does.
Ask
A declarative opt-in for a patch group to run as a view transition. Depends on gap 1.

4Patch content is parsed as HTML, also inside SVG and MathML

Today
Template content is parsed in the HTML namespace wherever the target sits. The parser also rewrites <image> to <img>.
Workaround
After every apply, native included, the script reparses with outerHTML = outerHTML in the parent’s namespace and restores SVG <image>. Preact does the same reparse.
Ask
Parse the content with the target range’s parent as the context element, as innerHTML does.

5A patch cannot wait for, or place, its styles

Today
A patch writes only into its range. It cannot add to <head> or wait for a stylesheet.
Workaround
Late stylesheets go out as a render-blocking <link> before the patch. Late <style> rules arrive inside the patch and the script moves them into precedence order in <head>. Without script they stay put and the cascade order can differ.
Ask
A patch group that can target several ranges, or a way to declare resources a patch must wait for.

6A patch with no matching range stays in the document

Today
With no range of that name, the <template for> stays in the DOM. This happens when the client rendered the boundary first or its parent was removed.
Workaround
The script removes leftover templates.
Ask
Define the behaviour. Consider discarding the patch or reporting it through the event in gap 2.

7The range name cannot be looked up, and old browsers see a comment

Today
No API maps a name to its range. In browsers without support the marker parses as a comment.
Cost
Libraries carry a second marker per boundary (React <!--B:0-->, Preact <!--$s:id-->). Preact measured +2.8 to +5.5 gzip bytes per boundary, mostly the repeated id.
Ask
A lookup from name to range, so one marker serves the browser, the fallback and hydration.

8At high counts, native can cost more than a script batch

Today
Same 300 ms policy: native and script are level up to 500; at 2,000, native is 222 ms and script-applied 113 ms. Stubbing $RP on native drops ScriptDuration to ~0, so that gap is not library script — it is in the browser’s apply/layout path. Open whether that is expected cost or a Chromium bug.
Ask
Worth a Chromium performance look, not a spec change. Separate from the no-hold vs classic@300 comparison, which is mostly cadence plus $RP.

Not verified: whether a large patch shows in pieces while its template is still parsing; name collisions with user content or a second root; back/forward cache.

What libraries should ship today

  1. Emit the platform markers: <?start name>…<?end> around the fallback and <template for> for the content.
  2. Follow each flushed group with one small script call. It is the fallback for other browsers and the place to cover the gaps above. Do not use a page-wide MutationObserver.
  3. Keep one protocol. SVG, view transitions, resume and late styles stay on the same markers, handled by that script, so each can be dropped when the platform covers it.
<!-- React PR #25 -->
<!--B:0--><!--$?--><?start name="B:0">Loading…<?end><!--/$-->
<!-- later -->
<template for="B:0">…content…</template>
<script>$RP("B:0")</script>

Classic sends <div hidden id="S:0"> plus $RC("B:0","S:0") instead. Marker names and script names are library-local.
