Declarative Partial Updates for streaming SSR: Preact and React results

How should preact-render-to-string and React Fizz stream Suspense results to the browser? This page collects what we measured for DPU (<template for>, <?start>), tested in Chromium, Firefox and WebKit with Playwright. Everything ran on one machine on one day. Claude (via Claude Code) wrote the test pages, the harness and these notes, working from my direction. The checks encode what I think the right behavior is, so please challenge them.

The short version
  • Preact: PRs #474 (head e1e62e6) and #490 (head 44c96f0) both fix real bugs in main (table rows, SVG and MathML namespaces). With no client JS they pass 26 of 26 checks, where main passes 23. Neither shows a timing cost, and each boundary adds about 3 to 6 gzip bytes.
  • React Fizz: the DPU branch passes all 28 checks without hydration in Chromium (native, the $RP fallback, and the polyfill with native support turned off), Firefox and WebKit. One check, nested-template, fails after hydration, but it fails on the baseline too, so DPU isn't the cause.

Script vs MutationObserver

The two ways to finish a streamed boundary in browsers without native DPU. MutationObserver: one observer in an init script watches for <template for> elements and applies each as it arrives (Preact PR #474, and the template-for polyfill used in the React runs). Script: each chunk carries its own tiny <script> that applies it directly, the way Fizz's $RC/$RP works (Preact PR #490, and the $RP fallback in React).

What the numbers say. Speed: no meaningful difference. Differences under about 16 ms are noise, and in React the two are within 2 ms of each other. The script is slightly lower in Firefox in the Preact runs (about 10 ms), which is the only gap that stands out. Size: the script costs more per boundary (about +24 raw and +2.7 gzip bytes over the observer, because every chunk carries its own call) but much less up front (about 300 bytes less once per page). The crossover is early: in raw bytes the observer page is smaller from about 13 boundaries up, and the 60 and 100 boundary pages are 92 and 171 bytes smaller gzipped. Interactivity: when client JS loads after the stream, the observer got the counter clickable sooner in Firefox (81 vs 121 ms); I haven't looked at the spread across runs, so treat that as a hint.

What differs by design. The observer is one mechanism for the whole page, and chunks are plain markup. The script makes control flow explicit and lets the harness see per chunk whether the browser had already applied the template natively (we use that in the React runs: the $RP call count and "ids that still had a template" columns in results.md). The Preact script variant defines a window.$RC global, which might collide with React's on a page that mixes the two. I haven't tested that.

Method and limitations

  • Correctness: 26 checks (28 for React). hydrate=off tests the stream and polyfill on their own. late runs after hydration, which can hide a patch that failed.
  • Timing: 5 runs with variants interleaved in random order. Patch lag is read from a MutationObserver plus a 16 ms layout scan, so it's only accurate to about 16 ms. Smaller differences are noise.
  • One machine. React ran against a local server and Preact against deployed Workers, with no throttling and no real wire compression. I didn't measure low-end CPUs, more than 100 boundaries, bfcache or buffering proxies.
  • Two Preact variants in the full report, local-end-stamp and local-react-style, come from commits I haven't pushed.
