Declarative Partial Updates for streaming SSR: Preact and React results

How should preact-render-to-string and React Fizz stream Suspense results to the browser? This page collects what we measured for DPU (<template for>, <?start>), tested in Chromium, Firefox and WebKit with Playwright. Everything ran on one machine on one day. Claude (via Claude Code) wrote the test pages, the harness and these notes, working from my direction. The checks encode what I think the right behavior is, so please challenge them.

The short version
  • Preact: PRs #474 (head e1e62e6) and #490 (head 44c96f0) both fix real bugs in main (table rows, SVG and MathML namespaces). With no client JS they pass 26 of 26 checks, where main passes 23. Neither shows a timing cost, and each boundary adds about 3 to 6 gzip bytes.
  • React Fizz: the DPU branch passes all 28 checks without hydration in Chromium (native, the $RP fallback, and the polyfill with native support turned off), Firefox and WebKit. One check, nested-template, fails after hydration, but it fails on the baseline too, so DPU isn't the cause.

Both PRs pass every check, including foreignObject, and no boundary is lost in any browser. Timing is within noise of main everywhere, and Firefox patches faster with either PR than with main. (An earlier head of #474, 6a02913, hung on foreignObject and could drop the last boundary in Firefox and WebKit. Both are fixed in the current head, and nothing here uses the old one.) On size, main compresses a bit better because it writes the boundary id three times where the DPU variants write it four. Each extra copy costs about 2.9 gzip bytes. The full report has the details.

React Fizz: declarative patching in Firefox and WebKit

These runs use the flight-ssr-bench fixture at React commit 71111fb9b4 (branch fizz/declarative-patching). I ported the 26 Preact checks, added 2 React-specific ones (x-css-precedence, x-style-precedence), and kept an isolated foreignObject page. Browsers were Chromium 156.0.8078.4, Firefox 157.0 and WebKit 27.2 from Playwright. The variants are: baseline ($RC), decl-native (Chromium DPU), decl-$RP (DPU markup, $RP script fallback), decl+polyfill (template-for polyfill). To test the fallbacks in Chromium, I turned native DPU off with --disable-blink-features=DocumentPatching.

Most of the 120 to 180 ms lag comes from Fizz's default batching window (unstable_declarativeBatchMs), not from DPU. With batchMs=0, every variant, including $RP and the polyfill, drops to 1 to 3 ms in all three browsers (Firefox: 2 ms for both; WebKit: 1 and 2 ms). So the $RP fallback and the polyfill cost nothing measurable beyond batching. Differences of around 300 ms in "last visible" just reflect which batch landed last. Results for the 16 and 100 boundary pages are in results.md.

Method and limitations

  • Correctness: 26 checks (28 for React). hydrate=off tests the stream and polyfill on their own. late runs after hydration, which can hide a patch that failed.
  • Timing: 5 runs with variants interleaved in random order. Patch lag is read from a MutationObserver plus a 16 ms layout scan, so it's only accurate to about 16 ms. Smaller differences are noise.
  • One machine. React ran against a local server and Preact against deployed Workers, with no throttling and no real wire compression. I didn't measure low-end CPUs, more than 100 boundaries, bfcache or buffering proxies.
  • Two Preact variants in the full report, local-end-stamp and local-react-style, come from commits I haven't pushed.
