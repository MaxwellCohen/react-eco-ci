template for in streaming SSR: results, batching and gaps

React and Preact stream late Suspense content as hidden HTML plus a script that moves it into place. <template for> lets the browser do that move instead. In our Chromium runs it used 37% to 55% less main-thread time than React's $RC at the same reveal policy, with level bytes and patch timing.

The main gap: a native patch applies the moment it's parsed, so it can't be batched. React's PR keeps its 300 ms reveal batching by turning native patching off whenever scripts run. How batching works explains the mechanism.

Why adopt

  • Content streams in without script in browsers that support it.
  • Main-thread time is 37% to 55% lower than $RC at the same reveal policy.
  • Bytes, patch timing and correctness are level or better.
  • Libraries share one standard wire format.

What's missing

  • A native patch can't be batched or delayed, so React applies patches in script when scripts run.
  • View transitions, SVG and MathML, style ordering and hydration state still need script.
  • Only Chromium supports it. Other browsers use the script fallback.
  • The 37% to 55% result comes from a benchmark build that batches on the server, not from the PR's client-side batching.

Why adopt

  1. It works before, and without, script. The browser applies a patch as it parses it. Under a strict Content Security Policy (CSP) that blocks inline scripts, the Preact test page still completed in Chromium. With today's format, every fallback stays on screen.
  2. It uses less main-thread time at React's reveal policy. With reveals grouped in the same 300 ms window React uses, a small script applying <template for> content used 37% less at 60 boundaries, 53% less at 500 and 55% less at 2,000. Native apply used 39% less at 60 and 48% less at 500.
  3. It costs no extra bytes or time to content. Whole documents are 6% to 8% smaller raw, and within about 1% after gzip from 500 boundaries up. Patch lag is level at the same policy.
  4. It fixed real bugs in Preact. The <template for> PRs pass 26 of 26 DOM checks in three browsers. Preact main passes 23. Table rows, SVG and MathML fail on main.
  5. It's a platform format. Libraries that emit the same markers get faster as browsers improve, and each gap the platform closes is script a library can delete.

How batching works

React batches reveals on purpose. The first boundary to complete starts a timer. Every boundary that completes before the timer fires is revealed with it, in one pass. The next group waits at least 300 ms after the previous reveal, so content doesn't pop in one boundary at a time.

A native <template for> can't wait for a timer (gap 1). So when scripts run, the PR takes the ranges away from the parser and applies the patches itself, on the same timer and with the same reveal function as $RC. This describes PR head 7b29f02 (November 12, 2026).

Step by step, with scripts on

  1. The server sends the shell. Each pending boundary is a fallback inside a range, followed by one script call: 
    <!--$?--><?start name="B:0">Loading…<?end><!--/$-->
<script>$RP()</script>
  2. $RP() disarms the ranges. It walks the document with a TreeWalker and replaces each <?start> and <?end> processing instruction with a comment. A comment isn't a patch target, so the browser leaves later <template for> elements in the DOM unapplied. It also stores each marker in a Map by id.
  3. $RP() starts watching the stream. It attaches a MutationObserver (child list only) to the element the stream is appended to. It records the shell's paint time in $RT on the next animation frame.
  4. The server sends each group of completed boundaries. Each group is one or more templates followed by an empty comment, the sentinel. The sentinel tells the runtime that every template before it is fully parsed. 
    <template for="B:0">…content…</template>
<template for="B:1">…content…</template>
<!---->
    If a group must wait for a stylesheet, or needs a helper the page doesn't have yet, the server writes <script>$RP()</script> instead of the sentinel.
  5. The runtime queues each template. When the observer sees the sentinel, it removes each template before it and looks up its marker. It changes the boundary's <!--$?--> to <!--$~--> (queued), so hydration doesn't client-render it while it waits. It then pushes the marker and the template content onto $RB, the batch array $RC also uses.
  6. The first entry in a batch sets the timer. If the shell hasn't painted yet, the reveal runs on the next animation frame, with a 250 ms timeout as a backup. Otherwise it runs at $RT + 300 ms. Between 2,000 and 2,300 ms after navigation start, it runs at 2,300 ms instead, as $RC does. It's always a timer, so templates parsed in the same task join the batch.
  7. $RV reveals the whole batch. This is the same function $RC uses. It swaps every fallback in the batch for its content, marks each boundary <!--$--> (complete), sets $RT to now and schedules hydration retries.
  8. The runtime cleans up at DOMContentLoaded. It disconnects the observer and queues any <template for> still in the document.

With scripts disabled or blocked, step 2 never runs. The processing instructions stay in place, and the browser applies each template as it parses it, with no batching. In Firefox and WebKit, the markers already parse as comments, so the script path above is the only path.

What's missing

  • React never uses the native path when scripts run. To batch on the client without holding bytes on the server, the PR disarms native patching and applies in script (How batching works). Native patching only happens with scripts disabled or blocked, and then it isn't batched.
  • The PR's client throttle has no equal-policy TaskDuration run yet. The 37% to 55% table uses the server-hold build. The PR-head numbers predate 7b29f02.
  • The React diff is large. PR #25 is thousands of lines across about 33 files, behind a flag that's off in every build. Most of the runtime code covers the platform gaps below.
  • Only Chromium supports it. Firefox and WebKit need the script fallback, and a strict CSP without a nonce blocks that.
  • A MutationObserver polyfill doesn't scale. It costs 2× classic at 500 boundaries and 6.7× at 2,000.
  • The evidence is thin in places. All runs used one machine. Main-thread cost was measured in Chromium only, with hydration off. We didn't measure slow CPUs, throttled networks, real wire compression or intermediate visual states.

Platform gaps: notes for web standards

Each item is something a streaming library needs that <template for> doesn't do natively in Chromium 156, with the script React or Preact uses instead. Formatted notes: platform gaps. Markdown to paste into an issue: platform-gaps.md.

1A patch can't be held, batched or scheduled

Today
The browser applies a patch while parsing it. No attribute, event or API can delay it or group it with others.
Cost
React batches reveals on a 300 ms throttle so content doesn't pop in one boundary at a time. Native apply is immediate. A server hold would batch, but it delays bytes, which React won't do.
Workaround
$RP() turns every <?start> into a comment after the shell, so the browser has nothing to patch. It then queues each template and reveals the batch on the $RC timer. See How batching works.
Ask
A way to apply patches together: a group that commits at its end, a frame-aligned commit, or a cancelable event before apply.

2No signal that a patch was applied

Today
No event fires when a range is patched.
Cost
The library must mark the boundary complete and retry hydration at that moment.
Workaround
With scripts on, the runtime applies the patch itself, so it knows when. A MutationObserver on the stream's parent finds new templates, and the server ends each group with an empty-comment sentinel instead of a script.
Ask
A patch event that names the range.

3A native patch can't join a view transition

Today
A native patch is a plain DOM change, outside startViewTransition, with no point at which to set per-element transition names.
Workaround
When the page uses <ViewTransition>, the script applies the batch inside one transition, as $RC does.
Ask
A declarative opt-in for a patch group to run as a view transition. This depends on gap 1.

4Patch content is parsed as HTML, also inside SVG and MathML

Today
Template content is parsed in the HTML namespace wherever the target sits. The parser also rewrites <image> to <img>.
Workaround
The script reparses the content in the parent's namespace and restores SVG <image>. Preact does the same reparse.
Ask
Parse the content with the target range's parent as the context element, as innerHTML does.

5A patch can't wait for, or place, its styles

Today
A patch writes only into its range. It can't add to <head> or wait for a stylesheet.
Workaround
Late stylesheets go out as a render-blocking <link> before the patch. Late <style> rules arrive inside the patch, and the script moves them into precedence order in <head>. Without script they stay put, and the cascade order can differ.
Ask
A patch group that can target several ranges, or a way to declare resources a patch must wait for.

6A patch with no matching range stays in the document

Today
If no range has that name, the <template for> stays in the DOM. This happens when the client rendered the boundary first or its parent was removed.
Workaround
The script removes leftover templates.
Ask
Define the behavior. Consider discarding the patch or reporting it through the event in gap 2.

7The range name can't be looked up, and old browsers see a comment

Today
No API maps a name to its range. In browsers without support, the marker parses as a comment.
Cost
Libraries carry a second marker per boundary (React <!--$?-->, Preact <!--$s:id-->). Preact measured 2.8 to 5.5 extra gzip bytes per boundary, mostly the repeated id.
Ask
A lookup from name to range, so one marker serves the browser, the fallback and hydration.

8At high counts, native can cost more than a script batch

Today
Under the same 300 ms policy, native and script-applied are level up to 500 boundaries. At 2,000, native takes 222 ms and script-applied 113 ms. With $RP stubbed out, native ScriptDuration drops to about 0, so the extra time isn't library script. It's in the browser's apply or layout path. We don't know yet whether that's expected cost or a Chromium bug.
Ask
A Chromium performance investigation, not a spec change. This is separate from the no-batching vs classic comparison, which is mostly cadence plus $RP.

Not verified: whether a large patch shows in pieces while its template is still parsing, name collisions with user content or a second root, and back/forward cache behavior.

What libraries should ship today

  1. Emit the platform markers. Wrap the fallback in <?start name> and <?end>, and send the content in <template for>.
  2. Run one small script after the shell. It's the fallback for other browsers, the place to batch reveals, and where the gaps above get covered. Observe only the element the stream is appended to, not the whole page.
  3. Keep one protocol. Handle SVG, view transitions, resume and late styles on the same markers in that script, so you can drop each one when the platform covers it.
<!-- React PR #25, head 7b29f02 -->
<!--$?--><?start name="B:0">Loading…<?end><!--/$-->
<script>$RP()</script>
<!-- later, one group -->
<template for="B:0">…content…</template>
<!---->

Classic sends <div hidden id="S:0"> plus $RC("B:0","S:0") instead. Marker names and script names are specific to each library.
